# 测评结果落库设计

## 1. 目标

将 Cloud-OpsBench 单案例测评请求及其产物持久化到 SQLite，支持运行后查看报告、分数和失败信息，并可根据案例、类型、状态和时间查询历史记录。

当前范围包括：

- `POST /api/ai-ops/evaluations`：保存为 `REPORT`。
- `POST /api/evaluations/runs`：保存为 `REPORT`。
- `POST /api/evaluations/scores`：保存为 `SCORE`。
- 每次接口调用单独产生一条记录；重复测同一个 case 不覆盖历史记录。

本期不做批量测评、分数趋势分析、报告分享和结果自动清理。

## 2. 概念与约定

一条记录代表一次测评接口执行，`type` 表示该次执行保存的主要产物，而不是运行模式：

| 接口 | `type` | 主要响应内容 |
|---|---|---|
| `/api/ai-ops/evaluations` | `REPORT` | 结构化诊断、Markdown 报告和工具轨迹 |
| `/api/evaluations/runs` | `REPORT` | 结构化诊断、Markdown 报告和工具轨迹 |
| `/api/evaluations/scores` | `SCORE` | Cloud-OpsBench 案例分数 |

数据库 `id` 使用自增整数作为主键。另保存 AIOps 执行产生的 `run_id`（UUID），用于和应用日志、工具轨迹关联；二者含义不同。

`/api/evaluations/runs` 与 `/api/evaluations/scores` 是两次独立的接口调用。即使 `dataset`、`case_id` 和配置相同，也代表两次独立模型运行；本设计不假定二者结果来自同一次推理。若未来需要对同一次运行同时产出报告和分数，应另行设计一个同时生成两类产物的运行接口或关联模型。

## 3. 数据表

新增 SQLite 表 `evaluation_record`，每次运行先创建 `RUNNING` 记录，运行结束后更新为 `SUCCEEDED` 或 `FAILED`。

这里的 `status` 表示测评执行/落库流程状态，不代替诊断质量状态：只要运行正常结束并生成可序列化的结果，即使报告中的 `diagnosis.status` 是 `INVALID_OUTPUT` 或 `EVIDENCE_UNVERIFIED`，记录仍为 `SUCCEEDED`，具体诊断状态保留在 `response_body`；只有执行异常或无法生成/保存结果时才记为 `FAILED`。

```sql
CREATE TABLE IF NOT EXISTS evaluation_record (
    id                    INTEGER PRIMARY KEY AUTOINCREMENT,
    run_id                TEXT NOT NULL UNIQUE,
    type                  TEXT NOT NULL CHECK (type IN ('REPORT', 'SCORE')),
    request_body          TEXT NOT NULL,
    response_body         TEXT,
    dataset               TEXT NOT NULL,
    case_id               TEXT NOT NULL,
    status                TEXT NOT NULL CHECK (status IN ('RUNNING', 'SUCCEEDED', 'FAILED')),
    error_message         TEXT,
    agent_profile         TEXT NOT NULL,
    profile_version       INTEGER NOT NULL,
    model_provider        TEXT,
    model_name            TEXT,
    started_at            TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP,
    completed_at          TEXT
);

CREATE INDEX IF NOT EXISTS idx_evaluation_record_case_started
    ON evaluation_record (dataset, case_id, started_at DESC);

CREATE INDEX IF NOT EXISTS idx_evaluation_record_type_status_started
    ON evaluation_record (type, status, started_at DESC);
```

### 字段说明

| 字段 | 用途 |
|---|---|
| `id` | SQLite 自增主键，对外用于历史记录查询。 |
| `run_id` | AIOps 运行 UUID，用于日志和轨迹关联；唯一。 |
| `type` | 产物类型：`REPORT` 或 `SCORE`。 |
| `dataset`、`case_id` | 数据集及案例标识，作为独立列便于过滤和统计；当前 dataset 为 `cloud-ops-bench`。 |
| `status` | 生命周期状态：`RUNNING`、`SUCCEEDED`、`FAILED`。 |
| `request_body` | 本次接口收到的 JSON 请求快照，存为 SQLite TEXT。敏感凭据不得写入。 |
| `response_body` | 成功后的规范化业务响应 JSON；运行中可为空。 |
| `error_message` | 失败摘要；成功时为空。避免保存密钥、完整异常堆栈或未经脱敏的敏感日志。 |
| `agent_profile`、`profile_version` | 本次实际使用的 Agent 配置名和版本。代码默认配置使用版本 `0`；显式配置版本保存实际版本号。 |
| `model_provider`、`model_name` | 记录本次实际模型身份，辅助复现；不记录 API Key。 |
| `started_at`、`completed_at` | 记录运行开始和完成时间。所有时间使用统一时区/格式（建议 UTC ISO-8601，或一致使用 SQLite UTC 时间）。 |

`request_body` 和 `response_body` 保存完整 JSON 文本，不另行展开高频变化的响应字段。查询和索引依赖的字段（dataset、case、类型、状态、配置和时间）单独存列。

## 4. 请求与响应快照

### REPORT

- `/api/ai-ops/evaluations` 保存收到的 `AIOpsRequest` 请求体。接口会强制设为 `REPLAY`，配置记录为当前生效的 `EVALUATION` profile。
- `/api/evaluations/runs` 保存收到的测评请求体，以及服务端实际解析出的 `agentProfile` 和 `profileVersion`。未显式提供版本时保存实际使用的当前生效版本；默认代码配置为版本 `0`。
- `response_body` 采用规范化 JSON，至少包含 `runId`、`mode`、`caseId`、`diagnosis`、`markdownReport` 和 `trace`。对于 SSE 接口，保存业务结果对象，不保存 SSE 分块帧的原始拼接文本。

### SCORE

- `/api/evaluations/scores` 保存收到的测评请求体以及实际使用的 profile/version。
- `response_body` 保存评分接口的完整 JSON 响应，包括 `caseId` 和 `scores`。
- 本期评分仍基于该次请求内部执行得到的 `AiOpsRunResult`；报告接口与评分接口分开调用时，不共用同一份模型运行结果。

## 5. 写入流程

### 同步报告和评分接口

1. 校验请求并解析实际使用的 dataset、case、Agent profile/version 和模型信息。
2. 创建 `RUNNING` 记录，写入 `run_id`、请求快照和运行元数据。
3. 执行 Agent；评分接口继续基于该次运行结果计算分数。
4. 成功时将规范化业务响应写入 `response_body`，更新为 `SUCCEEDED` 并设置 `completed_at`。
5. 执行失败时更新为 `FAILED`，写入安全的 `error_message` 和 `completed_at`，保留原请求记录。

### SSE 报告接口

1. 接口接受并校验请求后，先创建 `RUNNING` 记录，再启动异步测评。
2. Agent 成功时，先持久化完整规范化报告响应并更新为 `SUCCEEDED`，再发送完成事件。
3. Agent 失败时，保存失败状态和错误摘要，再发送错误事件。
4. 客户端断开不应直接删除记录；若应用在运行期间异常退出，遗留的 `RUNNING` 记录可供运维识别。是否将超时/进程重启遗留记录标成失败，需在实现时制定明确的超时策略。

落库失败时不得静默返回“测评已成功持久化”。SSE 运行应向客户端发送错误事件；同步接口应返回明确错误。实现应记录关联 `run_id` 便于排查。

## 6. 查询接口

建议新增：

```http
GET /api/evaluations?type=REPORT&caseId=trainticket/runtime/11&status=SUCCEEDED&page=0&size=20
GET /api/evaluations/{id}
```

- 列表接口返回轻量摘要：`id`、`runId`、`type`、`dataset`、`caseId`、`status`、profile/version、模型、开始/完成时间和失败摘要；不默认返回完整 trace。
- 详情接口返回完整请求和响应快照。
- `type`、`caseId`、`status` 为可选过滤项；分页参数应设置服务端最大 `size`。
- 暂不提供删除和修改历史记录的接口，已完成结果视为不可变快照。

## 7. 配置版本与可复现性

- 每次执行开始时读取一次 Agent profile 快照；运行期间即使用户应用了新版本，也继续使用已读取的版本。
- 保存实际生效的 `agent_profile` 和 `profile_version`，不能只保存请求中的字段：旧兼容接口不接收 profile 字段，`/api/evaluations/runs` 的 profile/version 也可能由服务端默认或解析。
- 版本 `0` 表示应用内置默认配置，不对应 `agent_profile_version` 表中的一行。
- 请求快照保留客户端实际提交的内容；执行元数据列保留服务端解析后的最终配置，两者不互相替代。

## 8. 数据保护

- 请求和响应内容按 JSON TEXT 存储；禁止记录模型 API Key、Authorization Header 等凭据。
- `trace` 可能包含日志片段、资源信息或业务数据。写入前按现有日志/工具数据脱敏要求处理，并限制详情接口访问权限。
- 本期不自动清理历史结果；部署前应确认 SQLite 磁盘空间及备份策略，并为后续保留期限/归档制定运维规则。
- 查询接口和测评执行接口应纳入管理员或受控网络访问范围。

## 9. 数据库迁移

新增 `src/main/resources/db/V3_evaluation_record.sql`，创建表和索引，并写入 `db_schema_version` 的 `V3` 版本记录。按项目当前迁移约定，由部署人员在升级应用前手动执行 V3；不得在应用启动时自动修改已有 SQLite 数据库。

## 10. 验收标准

1. 三个报告/评分入口均写入一条记录，类型分别为 `REPORT` 或 `SCORE`。
2. 成功记录包含请求快照、规范化响应、case/dataset、实际 profile/version、model 和完整时间信息。
3. 失败记录状态为 `FAILED`，保留请求和可读错误摘要，不留下永久无说明的空响应。
4. SSE 测评在客户端断开后仍能根据运行结果更新数据库记录。
5. 列表接口可按类型、case、状态分页查询；详情接口可取回完整快照。
6. 同一案例重复运行生成不同的自增 `id` 和 `run_id`，不覆盖历史结果。
7. `REPORT` 与 `SCORE` 记录不被误认为来自同一次执行；若未来要共用一次执行，需显式实现关联。
8. 落库和查询路径不泄漏 API Key；详情中返回的工具轨迹经过约定的脱敏处理。
